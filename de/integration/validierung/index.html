Server-Validierung

Der Server bestimmt den Spielzustand

Der Client läuft auf einem Gerät, das dem Nutzer gehört. Der Nutzer kann ihn verändern oder ganz ersetzen, z. B. Variablen in den Entwicklerwerkzeugen ändern, einen Godot-Export entpacken oder den Server direkt per curl ansprechen:

Daraus folgt eine klare Arbeitsteilung:

  • Der Client schickt nur, was der Spieler tun möchte: „nach rechts gehen“, „diesen Satz abgeben“, „für Eintrag 2 stimmen“.
  • Der Server entscheidet, was daraus folgt: neue Position, Punkte, Rundenende, Gewinner.

Das Multiplayer-Beispiel aus dem Kapitel Web-Sockets folgt bereits diesem Muster: Der Client schickt eine Richtung, die Position rechnet der Server aus.

Zeit und Reihenfolge

Auch wann etwas passiert, entscheidet der Server. Ein Countdown im Client ist nur Anzeige. Würde der Client melden „meine Zeit ist um“, könnte ein manipulierter Client unbegrenzt Zeit haben oder die Runde für alle beenden.

Ebenso prüft der Server bei jeder Aktion, ob sie gerade erlaubt ist. Ein gesperrter Button im Client verhindert keine doppelte Nachricht:

Datenformat prüfen

Neben dem Inhalt muss der Server auch das Format einer Anfrage prüfen. Sie kann falsch sein, durch fehlerhaften Code oder durch Manipulation. Bevor der Server die gesendeten Daten bearbeitet, muss er daher prüfen:

  1. Vorhanden? Eine fehlende Information ist in JavaScript undefined.
  2. Richtiger Typ? 5 ist eine Zahl, aber "5" oder "fünf" sind Text und kann zum Beispiel nicht direkt in Rechnungen verwendet werden.
  3. Sinnvoller Wertebereich? Ein Semester von -5 ist typkorrekt und trotzdem falsch. Texte brauchen eine Längenbegrenzung.

Auch der Client kann diese Prüfungen durchführen und dem Benutzer so sofort Feedback geben (z. B. ein rot markiertes Pflichtfeld). Das verbessert die User Experience, ersetzt aber nicht die Prüfung auf dem Server, denn der Client kann manipuliert oder umgangen werden.

Ungültige Daten dürfen den Server nicht abstürzen lassen

JSON.parse und request.json() werfen bei ungültigem JSON eine Exception. Bei HTTP bekommt dann nur dieser eine Request einen 500. Bei WebSockets beendet eine unbehandelte Exception im message-Listener dagegen den gesamten Server, und alle Spieler sind getrennt.

Sicherheit

Zu viele Anfragen

Ein Client kann den Server mit Nachrichten überfluten und ihn so für alle anderen unbenutzbar machen. Bei einer offenen WebSocket-Verbindung ist das besonders einfach. Abhilfe schafft ein Rate Limit, z. B. höchstens 30 Nachrichten pro Sekunde und Verbindung:

Werte vom Client dürfen nie direkt in eine SQL-Abfrage eingesetzt werden:

Beim Prepared Statement steht die Struktur der Abfrage fest, bevor die Werte eingesetzt werden. Der Wert kann die Abfrage nicht mehr verändern.

Fremden Text anzeigen

Dasselbe Prinzip auf der Client-Seite: Text, den andere Spieler geschrieben haben, darf nicht als Code interpretiert werden.

  • Browser
  • Godot

Ein Name wie <img src=x onerror=alert("I can run some code.")> wird mit innerHTML zu ausführbarem Code im Browser aller Mitspieler (Cross-Site-Scripting).

Ein RichTextLabel mit bbcode_enabled interpretiert Tags wie [font_size=200] oder [url] im Text anderer Spieler. ”[” ist also der Start eines Tags. Mit replace("[", "[lb]") wird daraus reiner Text.
