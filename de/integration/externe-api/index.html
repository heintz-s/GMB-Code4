Externe APIs anbinden

Der eigene Server als Client

Bisher hatte der eigene Server nur eine Rolle: Er hat Anfragen von Clients beantwortet. Er kann aber auch selbst Client sein und Anfragen an fremde Server stellen.

Typische externe APIs:

DienstBeispielWarum extern?
KI / SprachmodelleTextgenerierung, BildbeschreibungModell lokal nicht ausführbar
GeodatenKarten, Adresssuche, RoutenDatenbestand zu groß
Wetter, ZeitzonenAktuelle MesswerteDaten ändern sich laufend
ZahlungenKreditkarte, PayPalRegulatorik, Haftung
AuthentifizierungLogin über Google, DiscordPasswörter nicht selbst verwalten
DatenbankSpielstände, Highscores (z. B. Supabase, Firebase)Kein eigener Datenbankserver nötig

Technisch ist der Aufruf nichts Neues, es ist dasselbe fetch, das schon auf der Clientseite verwendet wurde, nur eben in Deno statt im Browser.

Interessant ist nicht der Aufruf, sondern warum er auf dem Server stattfinden muss.

Warum nicht direkt aus dem Client?

Die naheliegende Idee: Godot oder der Browser ruft die externe API direkt auf, der eigene Server bleibt außen vor. Ein direkter Aufruf wäre weniger Aufwand, als den Server dazwischen zu schalten.

Das funktioniert technisch, ist aber trotzdem fast immer falsch.

Der API-Key wäre im Client

Fast jede externe API verlangt einen API-Key zur Authentifizierung und Abrechnung. Steht dieser Key im Client-Code, ist er öffentlich:

  • Im Browser steht er im JavaScript und im Netzwerk-Tab der Entwicklerwerkzeuge.
  • In einem Godot-Export steht er in der .pck-Datei, die sich mit frei verfügbaren Werkzeugen entpacken lässt.
  • Er lässt sich auch nicht schützen, etwa durch Verstecken oder Verschlüsseln: Bei der Verwendung muss er im Klartext vorliegen und ist damit einsehbar.

Der Key gehört nicht dem Nutzer, sondern dem Betreiber der Anwendung. Liegt er trotzdem auf dem Gerät des Nutzers, kann dieser alles damit tun, was die Anwendung kann, und zwar im Namen und auf Kosten des Betreibers: z. B. über dessen PayPal-Konto Rückerstattungen auslösen, Kosten bei einer KI-API verursachen oder auf die Datenbank mit allen Spielerdaten zugreifen.

Weitere Gründe

  • Kontrolle: Auf dem eigenen Server lässt sich begrenzen, wie oft und mit welchen Werten die externe API aufgerufen wird.
  • Austauschbarkeit: Wechselt der Anbieter, muss nur der Server angepasst werden — nicht jeder bereits ausgelieferte Spiel-Build.
  • CORS: Viele APIs erlauben keine Browser-Anfragen. Von Server zu Server gilt CORS nicht.
  • Aufbereitung: Die Antwort der externen API enthält meist viel mehr, als der Client braucht. Der Server kann sie reduzieren.

Server dazwischen schalten

Die Lösung ist ein eigener Server, der die Anfrage entgegennimmt, mit dem Key anreichert, an die API weiterleitet und die Antwort an den Client zurückgibt. Der Key verlässt den Server nie.

  1. API-Key als Umgebungsvariable ablegen

    Nicht im Quellcode

    Der Key darf nicht direkt im Code stehen, sonst landet er z. B. im Git-Repository und bleibt dort auch nach dem Löschen in der Historie.

    Der Key kommt in eine Datei, die direkt mit .gitignore von der Versionsverwaltung ausgeschlossen wird. Dies muss gleichzeitig passieren, damit es nie zum Commit der Datei kommt und damit zum Hochladen ins Repository. Ein Key, der einmal gepusht wurde, gilt als veröffentlicht und muss beim Anbieter gesperrt und neu erzeugt werden.

    Auf Deno Deploy gibt es keine .env-Datei, da diese eben nicht im Repository liegt und damit auch nicht transferiert wird. Dieselben Variablen werden dort im Dashboard in den Einstellungen der App als Umgebungsvariablen eingetragen. Im Code ändert sich nichts: Deno.env.get("KI_API_KEY") liest lokal aus der .env, auf Deno Deploy aus den Einstellungen.

  2. Proxy-Endpunkt implementieren

  3. Server mit Berechtigungen starten

    Deno erlaubt standardmäßig weder Netzwerkzugriffe noch das Lesen von Umgebungsvariablen. Beides muss beim Start explizit freigegeben werden:

    • --allow-net erlaubt Netzwerkzugriffe, also Anfragen an die externe API (und das Bereitstellen des eigenen Servers)
    • --allow-env erlaubt dem Code, Umgebungsvariablen mit Deno.env.get() zu lesen
    • --env-file=.env lädt die Variablen aus der .env-Datei in die Umgebung, damit der Server darauf zugreifen kann

  4. Aus dem Client aufrufen

    Der Client kennt weder den Key noch den Anbieter. Er kennt nur die Schnittstellen des eigenen Servers, über die er Anfragen senden kann. Der Server übernimmt dann die Kommunikation mit der externen API.

    • Browser
    • Godot

    Die Antwort kommt wie in HTTP Request aus Godot über das Signal request_completed.

Auch Daten ohne Key über den Server holen

Manche APIs brauchen keinen Key, z. B. eine API für zufällige Wörter oder Quizfragen. Dann könnte jeder Client sie direkt aufrufen. In einem Multiplayer-Spiel ist das trotzdem falsch: Jeder Client bekäme ein anderes zufälliges Wort.

Was alle Spieler gemeinsam sehen sollen, holt der Server einmal ab und verteilt es.

Verwendung von externen APIs

Die Anfrage an die externe API kann aus verschiedenen Gründen erfolgen. Sie muss nicht unmittelbar durch eine Client Anfrage angestoßen werden.

Das Ergebnis der Anfrage kann dann vom Server verwendet oder per Broadcast an die Clients verteilt werden, zum Beispiel über WebSockets.

Der Server kann die Antwort auch zwischenspeichern oder Cachen, um sie den Clients zum passenden Zeitpunkt zur Verfügung zu stellen. Damit ist Timing ein wichtiges Thema bei der Verwendung von externen APIs. Daneben gibt es noch weitere Punkte, die beachtet werden müssen.

Latenz

Je nach API kann die Antwort länger auf sich warten lassen, z. B. durch lange Berechnungen oder schlechte Erreichbarkeit.

  • Im Client braucht es eine sichtbare Rückmeldung: Ladeanzeige, “denkt nach …”, deaktivierter Button
  • Der Anfrage-Button muss gesperrt werden, solange eine Anfrage läuft, sonst schickt ein Client mehrfach die gleiche Anfrage
  • Ein Timeout ist wichtig (AbortSignal.timeout), um nicht zu lange auf eine Antwort zu warten, die vermutlich nicht mehr kommt

Parallelisierung

Wird ein Aufruf erst gestartet, wenn er gebraucht wird, wartet das ganze Spiel bzw. die ganze Anwendung. Daher Anfragen immer so früh wie möglich starten, das Promise merken und dann mit await abholen, wenn das Ergebnis tatsächlich gebraucht wird.

Verlässlichkeit

Die externe API ist ein System, über das du keine Kontrolle hast. Sie kann langsam sein, ausfallen, ihr Format ändern oder dich sperren.

  • Fehler müssen mit try/catch abgefangen werden
  • Anfragen, die nicht erfolgreich waren (res.ok) müssen ebenfalls als Fehler behandelt werden
  • Bei Fehlern braucht es einen Plan B: eine Standardantwort, ein deaktiviertes Feature, eine verständliche Fehlermeldung - sonst kann der Client dauerhaft hängen bleiben

Antworten sind Fremddaten

Die Antwort einer externen API ist kein vertrauenswürdiger Inhalt. Bei KI-Antworten kommt hinzu, dass sie nicht deterministisch sind und damit noch weniger kontrollierbar.

Wichtig: Struktur der Antwort prüfen, bevor darauf zugegriffen wird. Und Text niemals ungeprüft als HTML ins DOM schreiben (textContent statt innerHTML).

Kosten

Je nach API kostet jeder Aufruf Geld, oder es gibt Nutzungsgrenzen.

  • Länge der Anfrage begrenzen (im Beispiel: 500 Zeichen)
  • Anzahl der Anfragen pro Client begrenzen (Rate Limiting)
  • Bei wiederkehrenden Anfragen: Antworten zwischenspeichern (Cache)
  • Im Test-Betrieb: feste Antworten statt echter Aufrufe verwenden
