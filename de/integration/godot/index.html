Godot als Client

Engine als Client

Bisher war der Client immer ein Browser. Für den Server ist es egal, woher eine Anfrage kommt, von einem Browser, einer Game Engine oder einem anderen Server: Er empfängt HTTP-Requests bzw. WebSocket-Nachrichten und antwortet.

Das bedeutet:

  • Der HTTP Deno Server funktioniert unverändert mit Godot als Client.
  • Der Deno Server aus dem Kapitel Web-Sockets ebenfalls. Ein Godot-Client und ein Browser-Client können sich dort begegnen und miteinander spielen.
  • Es ändert sich nur die Syntax auf Client-Seite: statt fetch und new WebSocket() gibt es in Godot entsprechende GDScript-Klassen.

Oberfläche: DOM und Nodes

Im Browser besteht die Oberfläche aus HTML-Elementen, in Godot aus Control-Nodes (Label, LineEdit, Button, …) in einer Szene. Die Idee ist dieselbe: Elemente holen, auf Benutzeraktionen reagieren, Text setzen.

  • Browser
  • Godot

@onready sorgt dafür, dass der Node erst geholt wird, wenn die Szene geladen ist — das entspricht dem defer beim <script>-Tag.

Fremden Text anzeigen

Im Browser textContent statt innerHTML verwenden, sonst wird aus einem Spielernamen ausführbarer Code (siehe Server-Validierung ). In Godot gibt es dasselbe Problem in kleinerer Form: Ein RichTextLabel mit bbcode_enabled interpretiert BBCode-Tags im Text anderer Spieler.

Beachte die Parallelen:

  • http.request(...) blockiert nicht — genau wie fetch. Das Spiel läuft weiter, die Antwort kommt später über ein Signal statt über await.
  • result entspricht dem catch-Zweig: Kam die Verbindung zustande?
  • response_code entspricht response.ok bzw. response.status: HTTP Antwort Statuscodes

Der Server sieht exakt denselben Request: gleiche Methode, gleicher Header, gleicher Body.

Achtung

Ein HTTPRequest-Node kann immer nur eine Anfrage gleichzeitig bearbeiten. Für parallele Requests werden mehrere Nodes benötigt, oder die Anfragen müssen nacheinander gesendet werden.

WebSockets aus Godot

Für laufende Kommunikation (Positionen, Chat, Spielzustand) wird WebSocketPeer genutzt. Anders als der HTTPRequest-Node ist das kein Node, sondern ein Objekt, das jeden Frame aktualisiert werden muss.

Als Beispiel dient der Multiplayer-Server aus dem Kapitel Web-Sockets . Er bleibt unverändert, es kommt nur ein Godot-Client neben den bestehenden Browser-Client. Zur Erinnerung das Protokoll:

RichtungTypInhalt
Server → Clientinit{ type, id, players } — nur an den neuen Client
Server → Clientjoin{ type, player } — jemand ist dazugekommen
Server → Clientupdate{ type, player } — jemand hat sich bewegt
Server → Clientleave{ type, id } — jemand ist gegangen
Client → Servermove{ type, dir } mit up, down, left oder right

Der Browser-Client wird im Beispielprojekt vom selben Server ausgeliefert. Er kennt dessen Adresse also aus location und muss nur das Protokoll anpassen.

Anders als der Browser-Client im Beispielprojekt wird ein Godot-Spiel nicht vom Server ausgeliefert, es gibt daher kein location. Die Adresse muss fest eingetragen oder vom Spieler eingegeben werden (siehe Server-Adresse ).

Der Browser ruft den Listener von sich aus auf, einmal pro Nachricht.

Godot muss selbst nachfragen: poll() holt neue Daten ab, dann werden alle wartenden Pakete in einer Schleife gelesen. _process() wird automatisch jeden Frame aufgerufen, solange set_process(true) gesetzt ist (Standard).

Das zweite Argument true lässt wie beim keydown auch die Tastenwiederholung beim Gedrückthalten zu.

_unhandled_input statt _process

Der Server macht pro move-Nachricht genau einen Schritt. Wie schnell sich eine Figur bewegt, hängt also davon ab, wie oft der Client sendet.

  • _unhandled_input mit true: eine Nachricht pro Tastendruck, beim Gedrückthalten über die Tastenwiederholung des Betriebssystems etwa 20–30 pro Sekunde. Das entspricht dem keydown im Browser.
  • _process mit Input.is_key_pressed(): eine Nachricht pro Frame, also rund 60 pro Sekunde. Die Godot-Figur wäre dadurch etwa doppelt so schnell wie die Figur im Browser.

Der Server im Beispiel prüft das nicht und führt jeden Schritt aus. Ein Client kann sich also einen Vorteil verschaffen, einfach indem er öfter sendet. Abhilfe schafft eine Regel auf dem Server, z. B. höchstens ein Schritt alle 50 ms pro Spieler (siehe Server-Validierung ).

Verbindungsstatus

Im Grundbeispiel aus dem Kapitel Web-Sockets gibt es die Events open, message und close. Godot kann nur den Status der Verbindung abfragen, wird aber nicht durch ein Event automatisch über Änderungen informiert. Um die Änderung des Zustands zu erkennen, muss Godot also regelmäßig in _process einen .poll() durchführen und dann den Verbindungsstatus prüfen.

Browser-EventGodot
open_process + .poll() + .get_ready_state() + prüfen auf Wechsel zu WebSocketPeer.STATE_OPEN
message_process + .poll() + get_available_packet_count() > 0, dann get_packet() (siehe Empfangen )
close_process + .poll() + .get_ready_state() + prüfen auf Wechsel zu WebSocketPeer.STATE_CLOSED
  • Browser
  • Godot

Das Skript vergleicht den Verbindungsstatus zum letzten gespeicherten Zustand. Ein Event entspricht dem Moment, in dem sich der Zustand ändert.

Besonderheiten von Godot

Server-Adresse: lokal und auf Deno Deploy

Derselbe Server kann prinzipiell beide Arten von Anfragen bearbeiten, HTTP und WebSockets. Im Multiplayer-Spiel könnten sich die Spieler zum Beispiel über HTTP einloggen und dann über WebSockets spielen.

Die Server-Adresse ist dazu über beide Protokolle erreichbar. Welches Schema in die URL gehört, hängt davon ab, was angesprochen wird und ob die Verbindung verschlüsselt ist:

lokalDeno Deploy
HTTP-Endpunkte (fetch, HTTPRequest)http://127.0.0.1:8000/...https://projekt-xyz.org.deno.net/...
WebSocket (new WebSocket, WebSocketPeer)ws://127.0.0.1:8000/...wss://projekt-xyz.org.deno.net/...

Das Dashboard von Deno Deploy zeigt die Adresse mit https://. Für die WebSocket-Verbindung muss daraus wss:// werden. Moderne Browser wandeln eine https://-Adresse bei new WebSocket() automatisch um, Godot nicht: WebSocketPeer.connect_to_url() akzeptiert nur ws:// und wss://.

Export-Ziel beachten

Godot kann in verschiedene Ziele exportiert werden, und das Ziel bestimmt, welche Regeln für die Netzwerkkommunikation gelten.

  • Web-Export (HTML5)
  • Desktop-Export

Das Spiel läuft im Browser und unterliegt damit allen Browser-Beschränkungen:

  • CORS gilt. Der Server muss Access-Control-Allow-Origin senden, sonst blockiert der Browser die Antwort (siehe CORS ). Das betrifft HTTP-Requests; der WebSocket-Handshake unterliegt nicht der Same-Origin-Policy.
  • Mixed Content. Läuft das Spiel unter https://, sind http:// und ws:// blockiert. Es müssen https:// und wss:// sein.
  • Kein UDP, keine direkten TCP-Sockets. Nur HTTP, WebSocket und WebRTC.

Das Spiel läuft als eigenständige Anwendung, außerhalb der Browser-Sandbox:

  • CORS gilt nicht. Der Header wird ignoriert, die Antwort wird nicht blockiert.
  • UDP möglich (PacketPeerUDP, ENetMultiplayerPeer) — geringere Latenz als WebSockets.
  • Zugriff auf das lokale Dateisystem, eigene Ports, etc.

Godots eigenes Multiplayer-System

Godot bringt mit dem High-Level Multiplayer API ein eigenes Netzwerksystem mit. Eine Godot-Instanz übernimmt dabei die Rolle des Servers: das Spiel eines Mitspielers oder eine eigene Instanz ohne Spieler. Eine solche Server-Instanz wird als Server-Build exportiert und bei einem Game-Server-Anbieter (z. B. Edgegap ) oder auf einem eigenen Server betrieben.

Übertragen wird wahlweise über:

  • UDP (ENetMultiplayerPeer): geringe Latenz, Pakete wahlweise zuverlässig oder unzuverlässig . Nur für Desktop-Exporte, Browser unterstützen kein UDP.
  • WebSockets (WebSocketMultiplayerPeer): funktioniert auch im Web-Export, über TCP aber immer zuverlässig.

Godot-Server eignen sich vor allem für Echtzeitspiele, bei denen die Spiellogik auf dem Server laufen soll. Ein Godot-Server kann z. B. die Physik berechnen, Kollisionen erkennen und die Positionen der Spieler synchronisieren.

Für ein einfaches rundenbasiertes Spiel reicht auch ein Webserver aus. Er funktioniert mit beliebigen Clients, nicht nur mit Godot, und übernimmt meist auch Accounts, Ranglisten oder externe Dienste wie KI-APIs.

Beide Server können auch kombiniert werden. In vielen match-basierten Online-Spielen kommen z. B. beide Ansätze gemeinsam zum Einsatz:

  1. Anmelden → Webserver: prüft den Login, lädt Inventar und Fortschritt.
  2. Match suchen → Webserver: Das Matchmaking stellt Spieler zusammen und startet eine Server-Instanz.
  3. Match spielen → Godot-Server: Die Clients verbinden sich für die Dauer des Matches mit dieser Instanz.
  4. Match beenden → Der Godot-Server meldet das Ergebnis an den Webserver, der es speichert.

Beispiel: Multiplayer mit ENet

Dasselbe Spiel ohne Deno-Server, dafür mit Godots Multiplayer-System: Ein Spieler übernimmt als Host die Rolle des Servers. Er hält die Positionen, spielt selbst mit und schickt 20-mal pro Sekunde den Stand an alle. Übertragen wird über UDP.
