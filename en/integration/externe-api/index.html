Connecting External APIs

The Server as a Client

So far, our own server had only one role: it answered requests from clients. But it can also act as a client itself and send requests to other servers.

Typical external APIs:

ServiceExampleWhy external?
AI / language modelsText generation, image descriptionModel cannot run locally
GeodataMaps, address search, routesData set too large
Weather, time zonesCurrent measurementsData changes constantly
PaymentsCredit card, PayPalRegulation, liability
AuthenticationLogin via Google, DiscordNo need to manage passwords yourself
DatabaseSave games, high scores (e.g. Supabase, Firebase)No own database server needed

Technically, the call is nothing new: it is the same fetch already used on the client side , just in Deno instead of the browser.

What matters is not the call itself, but why it has to happen on the server.

Why Not Directly from the Client?

The obvious idea: Godot or the browser calls the external API directly, and our own server stays out of it. A direct call would be less work than putting the server in between.

This works technically, but it is almost always wrong.

The API Key Would Be in the Client

Almost every external API requires an API key for authentication and billing. If this key is in the client code, it is public:

  • In the browser, it appears in the JavaScript and in the network tab of the developer tools.
  • In a Godot export, it is contained in the .pck file, which can be unpacked with freely available tools.
  • It cannot be protected either, e.g. by hiding or encrypting it: when used, it must be available in plain text and can therefore be read.

The key does not belong to the user, but to the operator of the application. If it is nevertheless on the user’s device, the user can do everything with it that the application can do, in the operator’s name and at the operator’s expense: e.g. trigger refunds via the operator’s PayPal account, cause costs with an AI API, or access the database with all player data.

Further Reasons

  • Control: On your own server, you can limit how often and with which values the external API is called.
  • Interchangeability: If the provider changes, only the server needs to be adapted — not every game build already shipped.
  • CORS: Many APIs do not allow browser requests. CORS does not apply between servers.
  • Processing: The response of the external API usually contains much more than the client needs. The server can reduce it.

Putting a Server in Between

The solution is your own server that receives the request, adds the key, forwards it to the API and returns the response to the client. The key never leaves the server.

  1. Store the API key as an environment variable

    Not in the source code

    The key must not be written directly in the code, otherwise it ends up e.g. in the Git repository and stays in its history even after being deleted.

    The key goes into a file that is excluded from version control via .gitignore right away. Both must happen at the same time, so that the file is never committed and thus never uploaded to the repository. A key that has been pushed once is considered public and must be revoked at the provider and regenerated.

    On Deno Deploy there is no .env file, because it is not in the repository and is therefore not transferred. The same variables are entered there as environment variables in the app settings in the dashboard. Nothing changes in the code: Deno.env.get("AI_API_KEY") reads from the .env locally and from the settings on Deno Deploy.

  2. Implement the proxy endpoint

  3. Start the server with permissions

    By default, Deno allows neither network access nor reading environment variables. Both must be granted explicitly at startup:

    • --allow-net allows network access, i.e. requests to the external API (and serving our own server)
    • --allow-env allows the code to read environment variables with Deno.env.get()
    • --env-file=.env loads the variables from the .env file into the environment so the server can access them

  4. Call from the client

    The client knows neither the key nor the provider. It only knows the endpoints of our own server, through which it can send requests. The server then handles the communication with the external API.

    • Godot

    As in HTTP Requests from Godot , the response arrives via the request_completed signal.

Fetching Data Without a Key via the Server, Too

Some APIs don’t need a key, e.g. an API for random words or quiz questions. Then every client could call them directly. In a multiplayer game, this is still wrong: every client would get a different random word.

Whatever all players should see together is fetched once by the server and distributed.

Using External APIs

The request to the external API can be made for various reasons. It does not have to be triggered directly by a client request.

The result of the request can then be used by the server or broadcast to the clients, for example via WebSockets.

The server can also store or cache the response to provide it to the clients at the right moment. This makes timing an important topic when using external APIs. There are also other points to keep in mind.

Latency

Depending on the API, the response can take a while, e.g. due to long computations or poor availability.

  • The client needs visible feedback: a loading indicator, “thinking …”, a disabled button
  • The request button must be disabled while a request is running, otherwise a client sends the same request several times
  • A timeout is important (AbortSignal.timeout) to avoid waiting too long for a response that will probably never arrive

Parallelization

If a call is only started when it is needed, the whole game or application has to wait. So always start requests as early as possible, keep the Promise, and retrieve it with await when the result is actually needed.

Reliability

The external API is a system you have no control over. It can be slow, fail, change its format or block you.

  • Errors must be caught with try/catch
  • Requests that were not successful (res.ok) must also be treated as errors
  • In case of errors, you need a plan B: a default response, a disabled feature, an understandable error message - otherwise the client may hang indefinitely

askAi, for example, must be written so that it never throws an exception, but returns a fallback value in case of an error. Otherwise the error is passed on to endRound, which aborts, and the round never ends:

Responses are external data

The response of an external API is not trustworthy content. AI responses are also non-deterministic and therefore even less controllable.

Important: check the structure of the response before accessing it. And never write text into the DOM as HTML without checking it (textContent instead of innerHTML).

Costs

Depending on the API, every call costs money, or there are usage limits.

  • Limit the length of the request (in the example: 500 characters)
  • Limit the number of requests per client (rate limiting)
  • For recurring requests: store responses (cache)
  • During testing: use fixed responses instead of real calls
