Godot as a Client

Engine as a Client

So far, the client has always been a browser. For the server, it doesn’t matter where a request comes from, whether from a browser, a game engine or another server: it receives HTTP requests or WebSocket messages and responds.

This means:

  • The HTTP Deno server works unchanged with Godot as a client.
  • So does the Deno server from the WebSockets chapter . A Godot client and a browser client can meet there and play together.
  • Only the syntax on the client side changes: instead of fetch and new WebSocket(), Godot has corresponding GDScript classes.

User Interface: DOM and Nodes

In the browser, the user interface consists of HTML elements; in Godot, it consists of Control nodes (Label, LineEdit, Button, …) in a scene. The idea is the same: get elements, react to user actions, set text.

  • Browser
  • Godot

@onready ensures that the node is only fetched once the scene has loaded — this corresponds to defer on the <script> tag.

Displaying text from others

In the browser, use textContent instead of innerHTML, otherwise a player name can turn into executable code (see Server Validation ). Godot has the same problem on a smaller scale: a RichTextLabel with bbcode_enabled interprets BBCode tags in other players’ text.

Achtung

An HTTPRequest node can only handle one request at a time. Parallel requests require multiple nodes, or the requests must be sent one after the other.

WebSockets from Godot

For ongoing communication (positions, chat, game state), WebSocketPeer is used. Unlike the HTTPRequest node, it is not a node but an object that must be updated every frame.

The multiplayer server from the WebSockets chapter serves as an example. It remains unchanged; only a Godot client is added alongside the existing browser client. As a reminder, the protocol:

DirectionTypeContent
Server → Clientinit{ type, id, players } — only to the new client
Server → Clientjoin{ type, player } — someone joined
Server → Clientupdate{ type, player } — someone moved
Server → Clientleave{ type, id } — someone left
Client → Servermove{ type, dir } with up, down, left or right

The second argument true also allows key repeat while holding a key, just like keydown.

_unhandled_input instead of _process

The server takes exactly one step per move message. How fast a character moves therefore depends on how often the client sends.

  • _unhandled_input with true: one message per key press; while holding a key, about 20–30 per second via the operating system’s key repeat. This corresponds to keydown in the browser.
  • _process with Input.is_key_pressed(): one message per frame, i.e. around 60 per second. The Godot character would be about twice as fast as the character in the browser.

The server in the example doesn’t check this and executes every step. A client can therefore gain an advantage simply by sending more often. A rule on the server helps, e.g. at most one step every 50 ms per player (see Server Validation ).

In Godot, the engine already has its own loop that calls _process(). From there, queue_redraw() triggers a redraw, whereupon the engine calls _draw(). For this, the script is attached to a Node2D.

Your own character is never moved locally

In both clients, a key press only sends the direction. The server calculates the new position and sends it back to everyone, including the sender. Only then is it drawn. This is the “server calculates” pattern from the Server Validation chapter.

Connection Status

The basic example from the WebSockets chapter has the events open, message and close. Godot can only query the connection status; it is not automatically notified of changes by an event. To detect a change of state, Godot must therefore regularly call .poll() in _process and then check the connection status.

Browser eventGodot
open_process + .poll() + .get_ready_state() + check for change to WebSocketPeer.STATE_OPEN
message_process + .poll() + get_available_packet_count() > 0, then get_packet() (see Receiving )
close_process + .poll() + .get_ready_state() + check for change to WebSocketPeer.STATE_CLOSED
  • Browser
  • Godot

The script compares the connection status with the last stored state. An event corresponds to the moment the state changes.

Godot Specifics

Server Address: Local and on Deno Deploy

In principle, the same server can handle both types of requests, HTTP and WebSockets. In the multiplayer game, players could for example log in via HTTP and then play via WebSockets.

The server address is reachable via both protocols. Which scheme belongs in the URL depends on what is being addressed and whether the connection is encrypted:

localDeno Deploy
HTTP endpoints (fetch, HTTPRequest)http://127.0.0.1:8000/...https://project-xyz.org.deno.net/...
WebSocket (new WebSocket, WebSocketPeer)ws://127.0.0.1:8000/...wss://project-xyz.org.deno.net/...

The Deno Deploy dashboard shows the address with https://. For the WebSocket connection, this must become wss://. Modern browsers convert an https:// address automatically in new WebSocket(), Godot does not: WebSocketPeer.connect_to_url() only accepts ws:// and wss://.

Consider the Export Target

Godot can export to different targets, and the target determines which rules apply to network communication.

  • Web export (HTML5)
  • Desktop export

The game runs in the browser and is therefore subject to all browser restrictions:

  • CORS applies. The server must send Access-Control-Allow-Origin, otherwise the browser blocks the response (see CORS ). This affects HTTP requests; the WebSocket handshake is not subject to the same-origin policy.
  • Mixed content. If the game runs under https://, http:// and ws:// are blocked. It must be https:// and wss://.
  • No UDP, no direct TCP sockets. Only HTTP, WebSocket and WebRTC.

The game runs as a standalone application, outside the browser sandbox:

  • CORS does not apply. The header is ignored, the response is not blocked.
  • UDP possible (PacketPeerUDP, ENetMultiplayerPeer) — lower latency than WebSockets.
  • Access to the local file system, own ports, etc.

Godot’s Own Multiplayer System

With the High-level multiplayer API , Godot comes with its own networking system. One Godot instance takes on the role of the server: either a player’s game or a separate instance without a player. Such a server instance is exported as a server build and run with a game server provider (e.g. Edgegap ) or on your own server.

Transmission works via either:

  • UDP (ENetMultiplayerPeer): low latency, packets optionally reliable or unreliable . Desktop exports only, browsers don’t support UDP.
  • WebSockets (WebSocketMultiplayerPeer): also works in the web export, but is always reliable via TCP.

Godot servers are particularly suitable for real-time games in which the game logic should run on the server. A Godot server can, for example, calculate physics, detect collisions and synchronize player positions.

For a simple turn-based game, a web server is sufficient. It works with any client, not just Godot, and usually also handles accounts, leaderboards or external services such as AI APIs.

Both servers can also be combined. Many match-based online games, for example, use both approaches together:

  1. Log in → web server: checks the login, loads inventory and progress.
  2. Find a match → web server: matchmaking groups players together and starts a server instance.
  3. Play the match → Godot server: the clients connect to this instance for the duration of the match.
  4. End the match → the Godot server reports the result to the web server, which stores it.
