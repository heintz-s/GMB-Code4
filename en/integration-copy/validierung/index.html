Server-Validierung

This content is not available in your language yet.

Der Client ist nicht vertrauenswürdig

Das ist der zentrale Satz dieses Kapitels, und er ist der eigentliche Grund, warum es überhaupt einen Server gibt.

Der Client läuft auf einem Gerät, das dem Nutzer gehört. Der Nutzer kann ihn lesen, verändern, umgehen oder komplett ersetzen. Alles, was der Client an den Server schickt, ist damit eine Behauptung — keine Tatsache.

Wie einfach das ist:

  • Browser: In den Entwicklerwerkzeugen lässt sich jede Variable ändern und jeder fetch-Aufruf von Hand wiederholen (Rechtsklick auf einen Request → „Copy as fetch”).
  • Godot: Ein Export lässt sich entpacken, Skripte lassen sich austauschen.
  • Ganz ohne Client: curl http://localhost:3000/student -X POST -d '{...}' — ein einziger Befehl. Es braucht keine Anwendung, um mit einem Server zu sprechen.

Daraus folgt eine einfache Arbeitsteilung:

Client-ValidierungServer-Validierung
ZweckBenutzerfreundlichkeitSicherheit und Korrektheit
BeispielRote Umrandung bei leerem FeldAblehnen mit Status 400
VorteilSofortige Rückmeldung, kein RequestKann nicht umgangen werden
Verzichtbar?Ja, mit schlechterer UXNein

Client-Validierung ist Komfort. Server-Validierung ist die eigentliche Prüfung. Beides ist sinnvoll — aber nur eines davon ist notwendig.

Was keine Absicherung ist

  • CORS. Ein Browser-Schutz für den Nutzer. Godot-Desktop-Builds, curl und jedes Skript ignorieren ihn vollständig.
  • HTTPS. Schützt die Daten unterwegs vor Mitlesen. Über den Inhalt sagt es nichts — auch Unsinn wird verschlüsselt übertragen.
  • Verstecken der URL. Jeder Request steht im Netzwerk-Tab.
  • Undokumentierte Endpunkte. „Weiß ja keiner” ist keine Zugriffskontrolle.

Was geprüft werden muss

Für jedes Feld, das vom Client kommt, in dieser Reihenfolge:

  • 1. Vorhandensein
  • 2. Typ
  • 3. Wertebereich
  • 4. Plausibilität

Ist das Feld überhaupt da? In JavaScript ist ein fehlendes Feld undefined — und undefined in die Datenbank zu schreiben ergibt selten das Gewünschte.

Ist es der erwartete Typ? "5" und 5 sind nicht dasselbe, und JSON kann jeden Typ transportieren — auch ein Objekt dort, wo eine Zahl erwartet wird.

TypeScript hilft hier nicht: Typen existieren nur zur Entwicklungszeit. await request.json() as Student ist eine reine Behauptung ohne jede Prüfung.

Liegt der Wert in einem sinnvollen Bereich? Ein Semester von -5 oder 10000 ist typkorrekt und trotzdem falsch.

Bei Texten gehört eine Längenbegrenzung dazu. Ohne sie kann ein Name 50 MB groß sein.

Ergibt der Wert im Kontext der Anwendung Sinn? Hat der Spieler diesen Punktestand überhaupt erreichen können? Gehört ihm das Objekt, das er verändern will? Ist er an der Position, von der aus er handelt?

Das ist die schwierigste und wichtigste Stufe — hier steckt die eigentliche Spiellogik.

Umsetzung in Deno

Eingaben prüfen

Statt as Student zu schreiben, wird eine Prüffunktion verwendet. Der Rückgabetyp data is Student sagt TypeScript, dass es sich nach einem true wirklich um einen Student handelt — diesmal zu Recht.

Im Endpunkt anwenden

Ein leerer Request-Body oder ein abgeschnittenes JSON lässt request.json() eine Exception werfen. Ohne try/catch stürzt der Handler ab — der Client bekommt einen 500, obwohl der Fehler bei ihm liegt.

Tipp

Für größere Projekte gibt es Bibliotheken, die solche Prüfungen aus einem Schema erzeugen, z. B. Zod oder Valibot . Das Prinzip bleibt identisch — nur die Schreibarbeit wird kürzer.

Passende Statuscodes

CodeBedeutungWann
400Bad RequestDaten fehlen, falscher Typ, unplausibler Wert
401UnauthorizedNicht eingeloggt
403ForbiddenEingeloggt, aber nicht berechtigt
404Not FoundEndpunkt oder Datensatz existiert nicht
409ConflictDatensatz existiert bereits
429Too Many RequestsRate Limit erreicht
500Internal Server ErrorFehler auf Serverseite — nicht für Client-Fehler

Fehlermeldungen sollen dem berechtigten Nutzer helfen, aber nicht mehr verraten als nötig. "Ungültige Anmeldedaten" ist besser als "Passwort falsch" — Letzteres bestätigt, dass der Benutzername existiert. Interne Details (Stacktraces, SQL-Fehler, Dateipfade) gehören ins Server-Log, nicht in die Antwort.

Autorität über den Spielzustand

Validierung geht über Formatprüfung hinaus. Die entscheidende Frage lautet: Wer darf einen Wert bestimmen?

Hier hilft auch keine Typprüfung. 999999999 ist eine gültige Zahl. Das Problem ist nicht das Format, sondern dass der Server einen Wert übernimmt, den er nicht selbst kennt.

Mögliche Antworten darauf, von einfach nach aufwendig:

  • Begrenzen
  • Plausibilität prüfen
  • Server berechnet

Eine Obergrenze aus den Spielregeln ableiten. Verhindert keinen gezielten Betrug, aber die offensichtlichen Fälle.

Den Wert gegen andere bekannte Daten halten: Spieldauer, Anzahl der Aktionen, bisheriger Punktestand.

Der Client schickt keine Ergebnisse, sondern nur Aktionen. Den Punktestand berechnet der Server aus seinem eigenen Zustand.

Das ist die einzige belastbare Lösung — und der Grund, warum ernsthafte Multiplayer-Spiele die Spielsimulation auf dem Server laufen lassen.

Auch WebSocket-Nachrichten validieren

Ein häufig übersehener Punkt: Bei HTTP wird meist an Validierung gedacht, bei WebSockets nicht. Dabei ist die Lage dort schlechter — die Verbindung bleibt offen, und Nachrichten kommen in hoher Frequenz.

Ohne Punkt 5 kann ein einzelner Client den Server mit Nachrichten überfluten und damit für alle anderen unbenutzbar machen. Bei einer offenen Verbindung ist das ohne Weiteres möglich.

NaN und Infinity sind gültige JavaScript-Zahlen und bestehen eine reine typeof-Prüfung. In Positionsberechnungen richten sie erheblichen Schaden an — deshalb Number.isFinite().

Ein Prinzip, drei Anwendungen

Server-Validierung ist kein eigenes Thema am Ende der Woche, sondern das, was die anderen Themen zusammenhält:

Nachtrag: SQL-Injection

Der Grund, warum im Kapitel Web API überall db.prepare(...) mit ?-Platzhaltern steht, gehört hierher:

Ein Aufruf von /student?studentNr=0 OR 1=1 liefert damit alle Datensätze zurück. Und 0; DROP TABLE student ist ebenfalls gültiges SQL. Der Eingabewert wird hier nicht als Wert behandelt, sondern als Programmcode.

Beim Prepared Statement steht die Struktur der Abfrage fest, bevor die Werte eingesetzt werden. Der Wert kann die Abfrage nicht mehr verändern — egal, was drinsteht.

Dasselbe Prinzip in anderer Form: Bei Text, der ins DOM geschrieben wird, textContent statt innerHTML verwenden. Sonst wird aus einem Spielernamen wie <img src=x onerror=alert(1)> ausführbarer Code (Cross-Site-Scripting).
