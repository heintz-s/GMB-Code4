Godot als Client

Die Engine ist nur ein weiterer Client

Bisher war der Client immer ein Browser. Für den Server macht das keinen Unterschied: Er empfängt HTTP-Requests bzw. WebSocket-Nachrichten und antwortet — wer die Anfrage gestellt hat, kann er nicht wissen.

Das bedeutet:

  • Der Server aus dem Kapitel Web API funktioniert unverändert mit Godot als Client.
  • Es ändert sich nur die Syntax auf Client-Seite: statt fetch und new WebSocket() gibt es GDScript-Klassen mit derselben Aufgabe.
  • Wer die Schnittstelle einmal verstanden hat, kann sie aus jeder Engine, jeder App und jedem Skript ansprechen.

Der wichtigste konzeptionelle Unterschied: Der Browser liefert Daten über Events, Godot über Polling im Frame-Takt. Das passt zur Spiel-Schleife, muss aber selbst angestoßen werden.

HTTP-Requests aus Godot

Für einmalige oder seltene Anfragen (Login, Highscore speichern, Spielstand laden) wird der HTTPRequest -Node genutzt.

GET: Daten abrufen

Beachte die Parallelen zu fetch:

  • http.request(...) blockiert nicht — genau wie fetch. Das Spiel läuft weiter, die Antwort kommt später über das Signal.
  • result entspricht dem catch-Zweig: Hat die Verbindung überhaupt geklappt?
  • response_code entspricht response.ok bzw. response.status: Hat der Server einen Fehler gemeldet?

Beides muss geprüft werden. Ein erfolgreich empfangener 404 ist aus Sicht des Netzwerks ein Erfolg, aus Sicht der Anwendung nicht.

POST: Daten senden

Der Server sieht exakt denselben Request wie vom Browser: gleiche Methode, gleicher Header, gleicher Body.

Achtung

Ein HTTPRequest-Node kann immer nur eine Anfrage gleichzeitig bearbeiten. Für parallele Requests werden mehrere Nodes benötigt, oder die Anfragen müssen nacheinander gesendet werden.

WebSockets aus Godot

Für laufende Kommunikation (Positionen, Chat, Spielzustand) wird WebSocketPeer genutzt. Anders als der HTTPRequest-Node ist das kein Node, sondern ein Objekt, das jeden Frame aktualisiert werden muss.

Zwei Dinge, die im Browser automatisch passieren und hier explizit gemacht werden müssen:

  1. socket.poll() in _process(). Ohne diesen Aufruf werden keine Daten gesendet oder empfangen. Der häufigste Anfängerfehler.
  2. Zustand prüfen vor dem Senden. connect_to_url() kehrt sofort zurück, die Verbindung steht aber erst einige Frames später. Ein send_text() direkt nach _ready() läuft ins Leere.

Der Server aus dem Kapitel Web-Sockets muss dafür nicht angepasst werden. Ein Godot-Client und ein Browser-Client können sich am selben Server begegnen und miteinander kommunizieren.

Export-Ziel beachten

Godot kann in verschiedene Ziele exportiert werden, und das Ziel bestimmt, welche Regeln für die Netzwerkkommunikation gelten.

  • Web-Export (HTML5)
  • Desktop-Export

Das Spiel läuft im Browser und unterliegt damit allen Browser-Beschränkungen:

  • CORS gilt. Der Server muss Access-Control-Allow-Origin senden, sonst blockiert der Browser die Antwort (siehe Web API ).
  • Mixed Content. Läuft das Spiel unter https://, sind http:// und ws:// blockiert. Es müssen https:// und wss:// sein.
  • Kein UDP, keine direkten TCP-Sockets. Nur HTTP, WebSocket und WebRTC.

Das Spiel läuft als eigenständige Anwendung, außerhalb der Browser-Sandbox:

  • CORS gilt nicht. Der Header wird ignoriert, der Request geht in jedem Fall raus.
  • UDP möglich (PacketPeerUDP, ENetMultiplayerPeer) — geringere Latenz als WebSockets.
  • Zugriff auf das lokale Dateisystem, eigene Ports, etc.

Wichtige Konsequenz

Dass CORS außerhalb des Browsers nicht gilt, ist kein Godot-Sonderfall, sondern die Regel. CORS ist eine Schutzfunktion des Browsers für den Nutzer — kein Schutz des Servers.

Ein Desktop-Build, ein Python-Skript oder ein curl-Aufruf ignorieren CORS vollständig. Wer seinen Server über CORS „absichern” will, hat ihn nicht abgesichert. Deshalb ist Server-Validierung kein optionales Extra.

Godots eigenes Multiplayer-System

Godot bringt mit dem High-Level Multiplayer API ein eigenes Netzwerksystem mit (ENetMultiplayerPeer, @rpc-Annotationen, MultiplayerSynchronizer). Damit lassen sich Spielzustände zwischen Godot-Instanzen synchronisieren, ohne HTTP oder WebSockets von Hand zu schreiben.

Für die Frage, was ein Backend tut, ist es hier trotzdem der falsche Einstieg:

  • Es funktioniert nur zwischen Godot-Instanzen. Ein Browser-Client oder eine Weboberfläche kann sich nicht verbinden.
  • Es beantwortet nicht, wie Daten dauerhaft gespeichert werden — eine Datenbank hängt weiterhin am eigenen Server.
  • Für externe Dienste (Zahlungen, KI-APIs, Statistiken) wird ohnehin HTTP benötigt.

In der Praxis werden beide Ansätze kombiniert: das High-Level API für die Spielsimulation, ein eigener Webserver für Accounts, Persistenz und externe Dienste.
